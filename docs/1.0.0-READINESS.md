# Is the surface actually working? A feature-by-feature audit

Measured 2026-08-14 against the reference fleet, on library `1.0.0b10` and
integration `2.14.0`. Companion to [ROAD-TO-1.0.md](ROAD-TO-1.0.md), which sets
the release bar; this file answers a narrower question that has to be settled
before that bar's clock can start: **does every feature we ship actually do
what it claims?**

## Why an ack is not evidence

This firmware acknowledges writes it then ignores. Of fourteen attributes
probed on 2026-08-14, **eight acked and kept their own value**. A feature that
"works" in the sense that no exception was raised is not a feature that works.

The same day produced three cases of code that looked healthy and did nothing:
the DTLS stdout producer (opened a session, wrote zero bytes, forever, with no
error), `async_open_cloud_playback` (dead at its first handshake step), and the
TUTK live path (needs a `p2pId` no device returns). All three passed a green
test suite, because the tests called the helpers directly and never asked who
called them.

So every row below is classified by evidence of **effect**, not existence:

| Class | Meaning |
|---|---|
| **A** | Effect observed on hardware - write confirmed by read-back, or media decoded |
| **B** | Exercised end to end, effect not independently confirmed (ack only) |
| **C** | Unit-tested only, or no verified call path from a user action |
| **D** | No caller - never executed outside its own tests |
| **E** | Known broken |

Scope is deduped by **entity key x model family** rather than by entity. 119
entities across 7 cameras are about 23 distinct features; the three model
families (A000088 DTLS, A001064 PTZ/SDES, A001513 battery/SDES) are where real
behavioural differences live.

## Verdict

**Two real defects found, both now fixed.** One was user-facing: a switch that
toggled and changed nothing.

Two of the five items in the first pass of this audit did not survive scrutiny,
and both corrections are recorded below rather than quietly edited out - an
audit that only ever finds things is not being read carefully enough either.

Everything else verified: 16 features in class A on hardware, including every
control that had never been confirmed by read-back, on all three model
families. One control stays at class B on purpose - see the PTZ buttons row.

## Findings, and what happened to them

**E1 - `switch.*_ir_light` acked and did nothing (A000088). FIXED.**
`nightVisionIRLight` accepted the write, returned success, and kept its
previous value - on both A000088 units, so model behaviour rather than one bad
camera. A user could toggle this switch in Home Assistant and nothing happened,
with no error. The entity is removed, a test pins its absence, and the library
setter now documents the measurement (it is kept: the attribute is real and
another model may honour it, but `True` is not evidence of change).

**E2 - `async_get_camera_attributes` returns nothing. DEPRECATED.** None for
an online A000088 and an online A001064, from two hosts. The obvious confound -
a broker evicting us for reusing the account's `mqttClientId` while Home
Assistant holds it - was **excluded** by repeating the call with a unique
client id, which changed nothing. Nothing calls it; camera state comes from
`async_get_all_device()`'s `properties`. Deprecated with removal at 1.0.0.

**The cause is not established, and an earlier version of this document said it
was.** "The camera never pushes the notification" was written on the strength
of a probe that logged zero inbound messages - but that probe's own control, a
self-publish meant to prove the session receives anything at all, also came
back empty, on a topic the broker's ACL would likely refuse. A test whose
control fails measures nothing. The credentials theory is also dead: the
streaming path uses the same smarthome MQTT credentials and works. The open
question is worth one clean experiment by whoever picks it up - subscribe on
these topics *during a live stream*, where the device channel is known to carry
traffic - because `async_open_cloud_playback` fails at the same MQTT step, and
one cause may explain both.

**E3 - `async_open_cloud_playback`** - deprecated in `1.0.0b10`. Removal owed
at 1.0.0.

**D1 - `custom_components/aidot/sd_playback.py` had no importer. REMOVED.**
Three helpers reachable only from their own tests, shipped in every HACS
snapshot, left over from an SD-playback stage closed as not feasible. The SD
browser is unaffected.

**D3 - `async_open_live_stream` (TUTK)** - accepted with a stated reason; item
4 of ROAD-TO-1.0 already put this path out of scope.

## Two corrections to the first pass of this audit

Both were called findings and neither was one. They are kept here rather than
edited away, because an audit that never corrects itself is not being read.

**"D2 - the `wifi_rssi` sensor never materialises" was wrong.** No entity
appears because the description sets `entity_registry_enabled_default=False` -
it is an opt-in diagnostic, exactly as intended. And the data is there: all
seven cameras report `networkRssi`, from -11 to -62 dBm. The mistake was
inferring dead code from an absent entity without checking why it was absent.

**"C1 - the A001064's controls cannot be read back at all" was wrong.** It is
true that the PTZ model has no local control and that E2 is broken, but a third
read-back path was sitting in plain sight: the coordinator's device-properties
poll, which is what populates every entity. Driving Home Assistant's own
service and reading the entity back confirmed `speaker_volume` 2 -> 3 and
`auto_tracking` on -> off within 25 s, both then restored. So the PTZ family is
verifiable after all, by the path users actually exercise - and that method is
cheaper than the LAN sweep, needs no credentials beyond the HA token, and works
on every model.

## Deliberately not tested, and why

- **The 7 sirens.** Firing a camera alarm in an occupied house is not a test,
  it is an incident. Same reasoning that makes two-way audio tests play silence.
- **Reboot / factory-reset / SD-format.** None exist. All 11 buttons are PTZ
  movement, which is why button testing carried no destructive risk.
- **Battery-camera controls (A001513).** Not swept, to avoid waking two battery
  cameras repeatedly for a settings probe. Their controls share the code path
  verified on the A000088; the wire attributes they accept may differ.

## What the countdown depends on

ROAD-TO-1.0's remaining bar is two weeks with no streaming-breaking release.
Nothing here is streaming-breaking: E1 was a settings switch, E2 is an uncalled
API, D1 was dead code. So none of them reset that clock - but shipping the
fixes starts a release, and that does.

So the clock starts at **the release that carries these fixes**, not at the
audit. What it now rests on is a surface where every user-facing feature has
been exercised for effect on at least one model of each family, the two defects
that turned up are closed, and the method for checking the next one is written
down: drive Home Assistant's own service, wait one coordinator poll, read the
entity back. Anything that acks and does not change is not shipped.

## How to re-run this

The cheap path, no credentials beyond the HA token, works on every model:

    # read -> write via the real service -> wait one poll -> read back -> restore
    curl -H "Authorization: Bearer $TOKEN" $HA/api/states/<entity>
    curl -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
         -d '{"entity_id":"<entity>"}' $HA/api/services/switch/turn_off
    sleep 30 && curl -H "Authorization: Bearer $TOKEN" $HA/api/states/<entity>

The LAN sweep is stronger where it applies (it reads all 58 attributes and
needs no HA at all) but only the mains A000088s advertise local control, and it
must run from a host on the LAN - macOS blocks the UDP discovery and the TCP
control socket for a non-permitted binary, so it runs from the LAN runner.

For library-level paths with no entity, reproduce the destination synthetically
before spending hardware cycles: a `testsrc` + `sine` MPEG-TS through the exact
argv the code composes caught the RTSP-push AAC failure in seconds, after three
hardware attempts had failed short of it for unrelated reasons.
