# Is the surface actually working? A feature-by-feature audit

Measured 2026-08-14 against the reference fleet, on library `1.0.0b10` and
integration `2.14.0`. Companion to [ROAD-TO-1.0.md](ROAD-TO-1.0.md), which sets
the release bar; this file answers a narrower question that has to be settled
before that bar's clock can start: **does every feature we ship actually do
what it claims?**

## Why an ack is not evidence

This firmware acknowledges writes it then ignores. Of fourteen attributes
probed on 2026-08-14, **eight acked and kept their own value**. A feature that
"works" in the sense that no exception was raised is not a feature that works.

The same day produced three cases of code that looked healthy and did nothing:
the DTLS stdout producer (opened a session, wrote zero bytes, forever, with no
error), `async_open_cloud_playback` (dead at its first handshake step), and the
TUTK live path (needs a `p2pId` no device returns). All three passed a green
test suite, because the tests called the helpers directly and never asked who
called them.

So every row below is classified by evidence of **effect**, not existence:

| Class | Meaning |
|---|---|
| **A** | Effect observed on hardware - write confirmed by read-back, or media decoded |
| **B** | Exercised end to end, effect not independently confirmed (ack only) |
| **C** | Unit-tested only, or no verified call path from a user action |
| **D** | No caller - never executed outside its own tests |
| **E** | Known broken |

Scope is deduped by **entity key x model family** rather than by entity. 119
entities across 7 cameras are about 23 distinct features; the three model
families (A000088 DTLS, A001064 PTZ/SDES, A001513 battery/SDES) are where real
behavioural differences live.

## Verdict

**Not yet clean. Two class-E defects and three class-D leftovers.** One of the
E's is user-facing: a switch that toggles and changes nothing.

The rest of the surface verified well: 13 features moved to class A on hardware
today, including every control that had never been confirmed by read-back.

## Findings that need action before 1.0.0

**E1 - `switch.*_ir_light` acks and does nothing (A000088).** `nightVisionIRLight`
accepts the write, returns success, and keeps its previous value. Confirmed on
both A000088 units, so it is model behaviour, not one bad camera. A user can
toggle this switch in Home Assistant and nothing happens, with no error. This
is the exact defect class that removed `SdcardRecord_Enable` from the switch
set before it shipped; this one shipped. Either remove the entity or gate it to
a model family where a read-back is confirmed. **Unresolved.**

**E2 - `async_get_camera_attributes` returns nothing.** The MQTT
presence-announce attribute read returned no data for an A000088 and an
A001064, from two different hosts, with both cameras online. Nothing calls it -
the integration reads camera state from `async_get_all_device()` properties,
which works - so no user is affected today. It is a public API that does not
work. **Unresolved.**

**E3 - `async_open_cloud_playback`** - already deprecated in `1.0.0b10`, with
removal scheduled for 1.0.0. Resolved as far as this release goes; the removal
is owed at 1.0.0.

**D1 - `custom_components/aidot/sd_playback.py` has no importer.** Three
helpers (`sd_play_identifier`, `parse_sd_play_identifier`, `find_record`),
reachable only from their own tests, shipped in every HACS snapshot. They were
scaffolding for SD playback stage 3, which is closed as not feasible. Remove or
state why they stay.

**D2 - the `wifi_rssi` sensor never materialises.** A sensor description exists
and produces no entity on any camera in the fleet. Either the attribute is
named differently on the wire or no model reports it; either way the
description is dead weight and its absence has never been explained.

**D3 - `async_open_live_stream` (TUTK)** - documented in `1.0.0b10` as unusable
(no `p2pId` on any device, native libraries not redistributable). Accepted with
a stated reason rather than fixed; item 4 of ROAD-TO-1.0 already decided this
path is out of scope.

**C1 - the A001064's controls cannot be read back at all.** It does not
advertise local control (a subnet sweep finds only the two A000088s), and the
only other read-back path is E2. So `ptz_tracking` - and any future control on
the PTZ model - cannot be verified by the method used everywhere else in this
document. This is a **tooling gap, not a known defect**, and it is the single
biggest hole in this audit: an entire model family's controls rest on class B
evidence. Fixing E2 would close it.

## Deliberately not tested, and why

- **The 7 sirens.** Firing a camera alarm in an occupied house is not a test,
  it is an incident. Same reasoning that makes two-way audio tests play silence.
- **Reboot / factory-reset / SD-format.** None exist. All 11 buttons are PTZ
  movement, which is why button testing carried no destructive risk.
- **Battery-camera controls (A001513).** Not swept, to avoid waking two battery
  cameras repeatedly for a settings probe. Their controls share the code path
  verified on the A000088; the wire attributes they accept may differ.

## What the countdown depends on

ROAD-TO-1.0's remaining bar is two weeks with no streaming-breaking release.
Nothing in this audit is streaming-breaking: E1 is a settings switch, E2 is an
uncalled API, and the D items are dead code. So they do not reset that clock -
but shipping fixes for them does start a new release, which does.

The honest sequence is to land E1, D1 and D2 together in one release, decide E2
(fix or deprecate), and start the clock from that release rather than from
today.
